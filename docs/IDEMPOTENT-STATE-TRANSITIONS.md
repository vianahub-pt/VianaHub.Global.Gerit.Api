# Auditoria de transições idempotentes

Inventário anterior à alteração funcional, produzido em 01/11/2026 na branch `refactor/idempotent-state-transitions`, base `161c2a3c2fc7de8d3c3784c9a8ded2ccf8241b70` (igual a origin/develop após fetch). Foram auditados 45 recursos de Identity, Billing, Business e Job, incluindo recursos só registrados em DI e vínculos com chaves compostas.

## Contrato e classificação

Actions (`c74a5a1`) permanece a referência: intenção repetida de Activate/Deactivate aceita, sem ignorar existência ou recurso deletado; Delete aceita o estado resultante no domínio, enquanto o lookup HTTP/AppService mantém 404/410. Categoria A: rejeição exclusivamente por estado-alvo já atingido. Categoria B: invariantes de negócio. Categoria C: existência, identidade, auditoria e integridade. Somente A é removida.

As regras abaixo são as existentes ANTES da correção. `A→removida` registra a decisão por regra; `C→preservar` inclui os guards explícitos de recurso deletado em Activate/Deactivate. Regras B dos recursos especiais são mantidas. Nenhum validator de Create/Update é esvaziado ou relaxado.

## Ordem e particularidades preservadas

Nos recursos comuns, a entidade é mutada no AppService antes de persistir e, quando o caminho usa o serviço de domínio, antes da validação. Não se deve exigir o estado anterior nesse ponto. ClientContactPerson persiste diretamente no repository; isso permanece. ClientAddress mantém validações completas de endereço em Activate/Deactivate via Update. Seu Delete foi encaminhado para a operação de domínio correta, preservando `CannotUpdateDeleted` para Update e os guards de lookup.

DeleteVisitTeam e DeleteVisitContact usam mensagens genéricas `IsDeleted`, mas o único predicado é `IsDeleted == false`: são categoria A em Delete. Os mesmos predicados em Activate/Deactivate são categoria C e permanecem. ModifiedBy/Id/tenant/FKs não são removidos.

Os catálogos cujo Deactivate tinha somente Id + AlreadyInactive não possuíam guard explícito CannotDeactivateDeleted nessa operação. Não se inventam novas regras nesta mudança: o AppService/repository continua rejeitando entidades removidas, conforme o contrato existente. Validators sem regras específicas (EmployeeTeam, VisitAddress) permanecem sem novas regras. Nenhuma transição ressuscita recursos.

A lookup semantics do HTTP para recursos soft-deleted permanece: Domain state transition is idempotent; HTTP lookup semantics for already-soft-deleted resources remain unchanged. Ausência ou entidade não recuperável continua sendo 404/410 conforme cada AppService. A matriz de testes conserva os códigos existentes por recurso.
